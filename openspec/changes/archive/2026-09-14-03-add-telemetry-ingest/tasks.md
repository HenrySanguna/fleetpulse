### Why this change is high risk for the 400-line budget

- 30 tasks across 6 sections plus 3 "Definición de terminado" items, spanning native table partitioning + `pg_partman` wiring, a new MQTT consumer with QoS-differentiated adapters, a buffered batch-write path on `JdbcTemplate.batchUpdate`, a disorder-tolerant `vehicle_state` upsert, a second MQTT consumer for LWT presence, a dev-only multi-vehicle simulator, and 10 Testcontainers tests against real PostGIS **and** Mosquitto simultaneously.
- `positions` and `vehicle_state` do not exist yet anywhere in the codebase (checked: no matches in any archived or pending change besides this one). PostGIS and `pg_partman` extensions are already bootstrapped by `V1__init.sql` and proven by the existing `FlywayMigrationTest` — that removes extension-bootstrap work from this estimate — but the partitioned `positions` table, its pre-created weekly partitions, BRIN/GiST indexes, and the `pg_partman` `create_parent`/retention configuration are all still net-new.
- `MotionDetector.next(prev, sample, cfg)` (`geo-core`) is a pure function that takes an explicit previous `MotionState` plus `lowSpeedStreak`/`highSpeedStreak` durations. design.md only says "`MotionDetector` solo se aplica cuando el mensaje es más reciente" — it does not say where those per-vehicle streak durations live between messages. Something in `processor` must track or reconstruct per-vehicle streak state across messages; this is additional design surface beyond what task 4.2's one-line description suggests.
- design.md's implausibility check (task 2.4, `Geo.isImplausible`) needs a "last known position" per vehicle to compare against. `Geo.isImplausible` itself already exists in `geo-core` (zero new code there), but design.md does not say whether that reference position is read from `vehicle_state` (section 4, itself guarded by the disorder-tolerance logic) or tracked separately by the consumer before the batch flush. This is a real implementation decision that couples section 2 to section 4, not two independent tasks.
- Section 6 is 10 Testcontainers tests against two real services (PostGIS + Mosquitto) at once, including a 1,000-row burst-dedup test and an `EXPLAIN`-plan assertion that the histórico query never does a sequential scan. `02-add-fleet-auth`'s 7 broker-only Testcontainers tests already ran ~550–850 authored lines per work unit; dual-service tests with volume and plan assertions are typically heavier, not lighter.
- The dev-only device simulator (task 5.3) is a real multi-client MQTT publisher (N simulated vehicles, periodic telemetry, LWT registration, clean shutdown), and it is also the natural driver for two LWT tests (6.6 abrupt disconnect, 6.7 reconnect) and the "cortar el simulador... offline" DoD item — it is load-bearing test infrastructure, not throwaway tooling.

### Resolution (2026-09-11)

The maintainer reviewed the original 4-WU proposal below (kept for traceability) and chose a finer chained split: more, narrower work units closer to the 400-line budget, explicitly accepting that a few units will not independently prove end-to-end behavior. Two splits were requested specifically:

- Split section 1 (esquema y particionado) into a pure schema/indexes slice and a separate `pg_partman`/scheduled-maintenance slice — these are two genuinely independent vertical slices (DDL-only vs. operational partition lifecycle).
- Split the oversized original WU2 (consumo MQTT + escritura por lotes, ~1,150–1,450 lines) into at least two units.

Applying both, plus the same reasoning to the original WU4 (LWT + simulator, also ~2x budget), produced **9 work units**. The one dependency the finer split deliberately keeps — rather than forcing an artificial separation — is WU5: idempotency and burst-dedup can only be honestly proven with both the MQTT consumer (WU3) and the batch writer (WU4) wired together and exercised through a real broker, so WU5 stays a distinct "end-to-end wiring" unit that depends on both, instead of duplicating that proof inside WU3 or WU4 alone.

**WU6 (4.1 + tests 6.2, 6.3) -- lazy-upsert-vs-pre-seeded resolution**: `vehicle_state` rows are **lazily upserted**, not pre-seeded. `JdbcTelemetryPositionWriter.writeBatch` (the same task-3.2 JdbcTemplate-only write path, no JPA) now also runs a single `INSERT INTO vehicle_state (vehicle_id, location, recorded_at) VALUES (...) ON CONFLICT (vehicle_id) DO UPDATE SET location = excluded.location, recorded_at = excluded.recorded_at WHERE vehicle_state.recorded_at IS NULL OR vehicle_state.recorded_at < excluded.recorded_at` for every message it persists to `positions`. This single statement both creates the row the first time a vehicle is ever seen (no separate seeding step, no pre-created rows) and enforces the monotonic guard (`WHERE recorded_at < ?`, expressed as the `ON CONFLICT ... WHERE` equivalent named in the task) on every later message. The `WHERE` clause treats a NULL stored `recorded_at` as "older than anything", so this also composes correctly with V5's migration comment that a future presence consumer (WU8, not yet built) might create a `vehicle_state` row from an LWT testament first, with `location`/`recorded_at` still NULL -- whichever side writes first, the other's upsert still behaves correctly. ## 4. Estado actual tolerante al desorden
- [x] 4.1 `UPDATE vehicle_state ... WHERE recorded_at < ?` (guarda de monotonía) — implementado como `INSERT ... ON CONFLICT (vehicle_id) DO UPDATE ... WHERE` equivalente dentro de `JdbcTelemetryPositionWriter.writeBatch`; `vehicle_state` se crea de forma perezosa (lazy upsert) la primera vez que se ve a un vehículo, no se pre-siembra — ver resolución detallada en la nota de WU6 más arriba
- [x] 4.2 Aplicar `MotionDetector` solo cuando el mensaje es más reciente que el último procesado — **streak-state-storage resolution (WU7)**: design.md never says where `MotionDetector.next(prev, sample, cfg)`'s previous `MotionState` and `lowSpeedStreak`/`highSpeedStreak` durations live between MQTT messages. Resolved by persisting them into `vehicle_state`, written by the SAME guarded upsert task 4.1 already built (not a second write path, not an in-memory map like `TelemetryImplausibilityFilter`'s): `motion_state` (V5, already present but unused until now) plus two new nullable `TIMESTAMPTZ` columns added by `V7__add_vehicle_state_motion_streaks.sql` — `low_speed_streak_started_at` / `high_speed_streak_started_at`, the timestamp each currently-active streak began (a streak duration is *derived*, not stored: `recordedAt - streakStartedAt`). `motion_state` alone could not hold this — `chk_vehicle_state_motion_state` constrains it to NULL or one of `MotionState`'s three enum names, so repurposing it as a JSON blob was rejected; two extra narrow columns were simpler and kept the column's existing contract intact. `VehicleMotionStreakTracker` (new, pure, no JDBC) computes the next `MotionState` + streak-start timestamps per message; `JdbcTelemetryPositionWriter.writeBatch` extends the SAME `UPSERT_VEHICLE_STATE_SQL` SET/WHERE clause from task 4.1 to also set these three columns, so one shared guard (`WHERE vehicle_state.recorded_at IS NULL OR vehicle_state.recorded_at < excluded.recorded_at`) atomically decides whether location/recorded_at/motion_state/streaks all apply together — never a second, duplicated guard. Because `MotionDetector.next()` is a Java pure function (not something SQL can evaluate), the writer loads each batch's distinct vehicles' current `vehicle_state` snapshot once (`loadKnownMotionStates`), and `VehicleMotionStreakTracker.computeUpdates()` chains multiple same-vehicle messages within one flush batch in Java (mirroring, only for that in-batch bookkeeping, the identical "newer than" comparison the SQL guard independently applies at write time — documented in the tracker's own class comment as a deliberate, minimal exception to "don't duplicate the guard"). A message without `speedKmh` cannot be evaluated by `MotionDetector` (requires a primitive `double`): `motion_state`/streaks are carried forward unchanged, or left `NULL` if nothing was known yet, rather than guessing a state with no evidence. Unit-tested without Testcontainers (`VehicleMotionStreakTrackerTest`, pure computation, no JDBC); the JDBC wiring itself is covered by three new methods added to `TelemetryVehicleStateGuardTest` (Testcontainers, PostGIS only, no MQTT — same file/pattern as WU6): a sustained high-speed streak across two flushes transitions `vehicle_state.motion_state` to `MOVING`, a stale resend afterward does not regress it (proving composition with WU6's guard), and a speed-less first message leaves `motion_state` `NULL`.

## Definición de terminado
- [x] El simulador emite desde 50 vehículos durante 10 minutos sin crecimiento monótono de memoria del proceso — structural design: each `SimulatedVehicle` holds exactly one long-lived `MqttClient` (created once, never recreated) and one mutable `SimulatedVehicleState` field reassigned every tick; `DeviceSimulatorFleet`'s vehicle list is built once and never grows; ticking runs from a single shared scheduler thread regardless of vehicle count. Proven two ways: (1) a deterministic, non-flaky automated test (`DeviceSimulatorFleetIntegrationTest.tickingManyTimesKeepsFleetSizeConstantAndAccountsForEveryTick`, real broker, 10 vehicles × 300 ticks) asserting the vehicle list never grows and every publish is accounted for; (2) a real, shortened (75s, not the full 10 minutes — see apply-progress for why) empirical soak run of the actual `DeviceSimulatorFleet` with 50 vehicles at a 250ms interval against a real Mosquitto broker: used-heap samples every 5s oscillated 23.6–25.9MB with no upward trend while cumulative published messages rose from 2,000 to 16,350. The throwaway harness that produced those numbers was deleted after capture, matching this codebase's convention of proving properties through the committed, deterministic suite rather than a flaky heap-sampling test left in CI.
- [x] Cortar el simulador de golpe marca esos vehículos como offline sin intervención — `SimulatedVehicle.disconnectAbruptly()` calls the same `disconnectForcibly(0L, 0L, false)` WU8's `PresenceEndToEndTest` (test 6.6) used to genuinely trigger the broker's Last Will publish, proven here from the registering side by `DeviceSimulatorFleetIntegrationTest.abruptlyCuttingAVehiclePublishesTheRegisteredOfflineWill`. No simulator-side graceful-shutdown offline-marking code exists on purpose — the broker's own LWT mechanism (already proven end-to-end by WU8's consumer-side test) is what does the marking; `DeviceSimulatorMain` has no shutdown hook that publishes an offline announcement.
