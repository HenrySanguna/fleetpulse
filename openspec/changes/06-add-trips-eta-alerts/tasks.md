### Why this change is high risk for the 400-line budget

- 18 numbered tasks across 4 sections (Viajes, ETA, Alertas, Rollups e informes) plus 7 test scenarios and 2 "Definición de terminado" items, spanning four fairly independent capabilities (trip segmentation, live ETA, a unified alerts pipeline, and historical rollups/reports) that only share the `processor` module and the `positions`/`vehicle_state` tables underneath them — unlike `05-add-geofencing`, this is not one cohesive evaluate→damp→dispatch pipeline, it is four separate verticals bundled into one change.
- **Real dependency analysis, not assumed from section order**: the launch prompt suggested trips "plausibly" gates ETA/alerts/rollups; checking each task's actual inputs shows this is only partly true. ETA (section 2) only needs a destination assignment plus `vehicle_state`/`positions` — no trip data. Alerts (section 3, speeding/idle) only need `vehicle_state`'s existing motion streaks (V7) plus new speeding/idle rules — no trip data either. Rollups' own hourly/daily aggregation (4.1/4.2) reads raw `positions`, not trips. The ONE genuine dependency on trips is task 4.3 (informe de actividad): the console's already-built `ActivityReportService`/`ActivityReportPageComponent` (built ahead of this backend against mock data, per the launch prompt) expects an `ActivityReport` shaped `{ summary, dailyDistances, trips }` — the `trips` field needs the `trips` table to exist. Trips is sequenced first because it is genuinely independent (no section depends on trips being absent) and because it is the one thing 4.3 cannot be built without, not because ETA/alerts are blocked on it.
- **Design gap found while forecasting, not yet resolved (deferred to the alerts work unit)**: design.md says "todas las alertas (geocerca, velocidad, ralentí, offline) comparten tabla" — a single unified `alerts` table. But `05-add-geofencing` already shipped `geofence_alerts` (V9) with its own `alert_type` enum (`enter`/`exit`/`dwell`) and its own MQTT publisher, and the console's already-built `Alert` model (`apps/console/.../alerts/models/alert.model.ts`) expects a DIFFERENT type union entirely: `geofence_enter | geofence_exit | speeding | excessive_idle | offline`. Section 3's own work unit must decide whether `alerts` (task 3.1) is a genuinely new unified table that geofence alerts get migrated/dual-written into, or a table that only carries the three NEW alert types while the console's `AlertsService` merges two backend sources — resolved when that work unit is actually implemented, not now, per this project's "note deviations, don't silently freelance" convention.
- **Console mock-data wiring folded into backend work units, not deferred**: per the launch prompt, `AlertsService`/`ActivityReportService` are already built against mock data specifically so this backend slots in underneath with minimal churn. The work unit that builds `GET /api/alerts` (task 3.4) also rewires `AlertsService` and adds the "mark as attended" control in the SAME work unit; the work unit that builds the activity-report endpoint (task 4.3) also rewires `ActivityReportService` and wires the rollup-fed charts (task 4.4) in the SAME work unit — mirroring how `05-add-geofencing`'s WU6 (backend CRUD) and WU7 (console editor) were split by "does this need a browser to prove," except here the console rewiring needs no browser, just the new endpoint's real response shape, so it stays with the backend work instead of becoming its own unit.
- **Architecture decision made while implementing WU1, not anticipated by design.md**: design.md's own vocabulary ("el vehículo pasa a moving... permanece en stopped") is MotionState terminology (geo-core's own MOVING/IDLING/STOPPED, already replayed live by `VehicleMotionStreakTracker` since `03-add-telemetry-ingest`) — not a gap in telemetry reporting. Resolved by replaying each vehicle's segmentation window through the SAME `VehicleMotionStreakTracker` bean (and therefore the same `MotionConfig` thresholds/debounce) the live write path already uses, rather than inventing a second, parallel speed-threshold heuristic. See `TripSegmenter`'s own class comment for the full reasoning.
- Every dual-container Testcontainers precedent in this codebase (`03`, `05`) exists because the feature under test genuinely runs on the live MQTT ingestion path. Trip segmentation explicitly does NOT (design.md: "no en el camino de ingesta") — its own Testcontainers tests correctly use a single PostGIS container, no Mosquitto, a deliberate deviation from the section 5 default documented in WU1's own evidence below, not an oversight.

Proven by `TripSchemaTest` (Testcontainers, same recipe as `GeofenceSchemaTest`).
- [x] 1.2 Tarea `@Scheduled` que segmenta ventanas con retraso deliberado — **WU1**: `TripSegmentationTask` (`backend/processor/.../trips/`), `@Scheduled(fixedDelayString = "PT5M")` (neither proposal.md nor design.md states an exact frequency — this change's own documented choice). Runs entirely over already-persisted `positions`, never on the live MQTT ingestion path, matching design.md's explicit "no en el camino de ingesta". **Architecture decision, not spelled out by design.md, documented per this project's "note deviations, don't silently freelance" convention**: design.md's own wording ("pasa a moving... permanece en stopped") is MotionState vocabulary, not a telemetry-reporting-gap concept — resolved by reusing the SAME `VehicleMotionStreakTracker` bean (and therefore the same `MotionConfig` thresholds/debounce) the live write path (`JdbcTelemetryPositionWriter`, change 03) already uses, replayed from an empty "known states" map per scheduled run. This is correct, not an approximation: the queried window always starts either at a vehicle's very first position (an "unseen vehicle", `VehicleMotionStreakTracker`'s own existing default) or right where the previous CLOSED trip left off — i.e. inside the stop that closed it — so seeding fresh is exactly right. See `TripSegmenter`'s own class comment for the complete reasoning.
- [x] 1.3 Umbral de parada configurable por organización — **WU1**: `organizations.trip_stop_threshold_secs` (V10, same migration), `NOT NULL DEFAULT 300` (matches design.md's own "por defecto 5 minutos"), `chk_organizations_trip_stop_threshold_secs CHECK (> 0)`. **Design decision, documented per the same convention**: unlike `FleetpulseGeofencingProperties`/`FleetpulseMotionDetectionProperties` (global app-level tuning values design.md never asked to vary per tenant), this threshold is explicitly required to be per-organization by the spec itself — a DB column, not a second Spring `@ConfigurationProperties` mechanism, is the only way for two organizations on the same `processor` deployment to genuinely have different values. `JdbcTripReader.loadVehiclesWithThreshold()` reads it once per scheduled run (one upfront lookup for every vehicle, the same shape `JdbcTelemetryPositionWriter.loadKnownMotionStates()` already established), not once per vehicle.
- [x] 1.4 Métricas por viaje: distancia (suma de tramos con `geo-core`), duración, ralentí, velocidad máxima y media — **WU1**: `TripSegmenter.addTrip()` (`backend/processor/.../trips/TripSegmenter.java`). Distance sums `Geo.distanceMeters` (geo-core, already idle since change 01) over every leg in the closed trip's span — zero new geo-core code, the same "reuse what already exists" shape `05-add-geofencing`'s WU2 established for `FenceTransition.from()`. `idle_secs` counts a leg only when BOTH its endpoints are already classified STOPPED/IDLING (a transition leg — the last MOVING reading into the first STOPPED one, or the reverse — is deliberately excluded from idle time: the exact instant motion changed within that interval is not observable from discrete samples, so it is attributed to neither bucket rather than double-counted). `max_speed_kmh` is the max device-reported `speed_kmh` across the trip's positions (a real point-in-time reading, preferred over an averaged geo-core-implied speed which would understate a true peak). `avg_speed_kmh` is `distance_km / (duration_secs / 3600)` for the whole trip span, including any sub-threshold idle time within it — a simple, common definition neither design.md nor proposal.md rules out.
- [x] 1.5 Idempotencia: reprocesar una ventana no duplica ni altera viajes ya cerrados — **WU1**: `uq_trips_vehicle_started_at` (V10) + `JdbcTripWriter`'s `ON CONFLICT (vehicle_id, started_at) DO NOTHING`. Unlike `vehicle_hourly`/`vehicle_daily`'s future `ON CONFLICT DO UPDATE` (whose whole point is absorbing genuinely late telemetry into an already-materialized rollup period), trips has no equivalent need: `TripSegmenter` never re-derives a different `started_at`/`ended_at` for a trip that was already closed and inserted, so a collision only ever means "already recorded," never "recompute and overwrite." `JdbcTripReader.lastClosedTripEndedAt()` is the watermark that keeps a re-run from re-reading already-covered history at all. Proven end-to-end by `TripSegmentationEndToEndTest.reprocessingTheSameWindowDoesNotDuplicateOrAlterAlreadyClosedTrips` (test 5.3 below).

## 2. ETA
- [x] 2.1 Asignación de destino a un vehículo — **WU2**: `V11__add_vehicle_destinations_and_eta.sql` (`backend/domain/src/main/resources/db/migration/`) adds `vehicle_destinations` — one row per vehicle (upsert on reassignment, not an append-only history like `trips`), `organization_id` denormalized (same convention `trips`/`geofences`/`geofence_alerts` already established). `PUT /api/vehicles/{vehicleId}/destination` (`VehicleDestinationController`/`VehicleDestinationService`/`JdbcVehicleDestinationRepository`, `backend/api/src/main/java/dev/fleetpulse/api/eta/`) assigns/replaces; `DELETE` clears (hard delete, idempotent no-op if already unassigned — unlike geofences, nothing else references this table by FK, so no soft-delete/`is_active` is needed). **Design decision, documented per this project's "note deviations, don't silently freelance" convention**: open to any authenticated dispatcher (not `hasRole('FLEET_ADMIN')`) — assigning a delivery destination is routine day-to-day dispatch work, the same class of action as reading fleet state, not fleet configuration like geofences/device credentials. Reuses `GeofenceController`'s own `GeoPointRequest` for the request body rather than a duplicate eta-specific point type. Cross-org vehicle hidden as 404, matching every other org-scoped endpoint's precedent.
- [x] 2.2 Cálculo de ETA por distancia con factor de sinuosidad y velocidad media reciente — **WU2**: `SinuosityEtaCalculator` (`backend/processor/.../eta/`) computes `Geo.distanceMeters` (geo-core, zero new geo-core code, same reuse convention `TripSegmenter`/WU1 established) between current position and destination, multiplies by a configurable sinuosity factor (`FleetpulseEtaProperties.sinuosityFactor`, default 1.3 — neither design.md nor proposal.md states an exact value, this WU's own documented choice, same undocumented-tuning-value precedent as `FleetpulseTripsProperties`'s processing delay), divides by the recent average speed. **"Velocidad media reciente" resolved by `JdbcRecentSpeedReader`**: reads the vehicle's own recently persisted `positions` over a configurable window (default 15 minutes) and averages speed via `Geo.distanceMeters`/elapsed time — the exact same formula `TripSegmenter.addTrip()`'s own `avgSpeedKmh` uses, applied to a short recent window instead of a whole trip. This is genuinely REAL, derived from real telemetry, never a fabricated constant; `FleetpulseEtaProperties.fallbackAverageSpeedKmh` (default 30.0) is used ONLY in the narrow, explicit case `JdbcRecentSpeedReader` reports fewer than two recent positions (a vehicle too new to have a real average yet), never silently substituted for an available real one. `FleetpulseEtaProperties.minEffectiveSpeedKmh` (default 5.0) floors the EFFECTIVE speed used in the division only (the recent average itself is untouched) so a stopped/idling vehicle gets a long-but-finite, clearly-margined estimate instead of an infinite/nonsensical one.
- [x] 2.3 Interfaz Java que aísla el cálculo para poder sustituirlo por un motor de rutas real — **WU2**: `EtaCalculator` (`backend/processor/.../eta/EtaCalculator.java`), a pure synchronous interface (`GeoPoint, GeoPoint, double -> EtaEstimate`) with zero JDBC/MQTT/Spring-context dependency of its own. `SinuosityEtaCalculator` is its only implementation today; design.md's documented post-MVP improvement (a real routing engine) can implement this same interface without any change to `EtaRecalculationDispatcher` or any other caller — the same pure-algorithm/impl-specific-data-access separation `TripSegmenter` (pure) vs `JdbcTripReader` (WU1) already established.
- [x] 2.4 Recálculo en el flujo en vivo y publicación al tópico de la organización — **WU2**: `EtaRecalculationDispatcher.recalculateAndDispatch()` wired into `JdbcTelemetryPositionWriter.writeBatch()`'s SAME guarded live path `GeofenceRuleDispatcher` (05-add-geofencing) already uses — reuses the EXACT same "newer than last known state" eligible-message subset (renamed `selectGeofenceEligibleMessages` → `selectLiveEligibleMessages` in that file, documented inline, since it now feeds two independent live-path consumers). Publishes to `fleet/{orgId}/vehicle/{vehicleId}/eta` (a per-vehicle topic, matching telemetry's own shape — ETA recalculates per live position for one specific vehicle, unlike alerts' sparse org-wide topic; design.md's "al tópico de la organización" read as "the org-scoped namespaced topic", the same namespacing every other topic in this system already uses). **Architecture decision, documented per the same convention**: publishes through a DEDICATED new `EtaMqttConfig` (long-lived outbound connection, QoS 0, ASYNC), not a reuse of `AlertMqttConfig`'s own outbound channel (QoS 2, synchronous) nor `MqttClientFactoryConfig`'s shared short-lived/fail-fast factory — checked both first, per the launch prompt's own instruction. ETA recalculates at telemetry's own high frequency (per live position, not per sparse alert event), so it needs telemetry's QoS-0/latest-value-wins semantics and an ASYNC publish so a slow/unreachable broker never blocks the guarded write path design.md requires to "escribir rápido" — reusing the alert channel would have forced either QoS 2 it does not need or per-message QoS/async overrides this codebase's MQTT config classes have never needed before. No new mosquitto ACL registration needed (same reasoning as `AlertMqttConfig`'s own comment — already covered by the existing `internal-services`/dispatcher wildcard ACLs).
- [x] 2.5 Presentación en la interfaz **como estimación con margen**, nunca como hora exacta — **WU2**: `libs/console-ui/src/lib/vehicle-detail/`'s `formatEtaLabel()` is the ONLY place this library renders an ETA — always `"~N min (± M min)"`, three states (no destination assigned / destination assigned but not yet recalculated ("Calculating…") / a real estimate with its margin), never a bare duration and never a clock time. Wired end to end: `VehicleStateResponse` (api module) carries the snapshot's `destinationLat`/`destinationLon`/`etaSeconds`/`etaMarginSeconds`/`etaCalculatedAt` (same "HTTP snapshot, then live MQTT stream takes over" shape `lat`/`lon`/`motionState` already established); the console's `fleet-message.mapper.ts` maps the new `eta` MQTT topic into a `VehicleEtaUpdate`, and `FleetStore.applyUpdate`/`mergeUpdate` merge it into `VehicleState` touching only the eta fields. `VehicleDetailComponent` (already built ahead of the backend against mock data, per the launch prompt) is wired to this real shape, not a parallel UI.

## 3. Alertas
- [x] 3.1 Migración Flyway: tabla `alerts` común a todos los tipos — **WU3**: `V12__add_alerts_and_migrate_geofence_alerts.sql` (`backend/domain/src/main/resources/db/migration/`). **Resolves the open design gap this change's own Review Workload Forecast flagged before any WU3 code was written, per the user's explicit decision (not inferred by this work unit)**: design.md's "todas las alertas ... comparten tabla" is implemented as a genuinely NEW unified `alerts` table, not a table that only carries the three new types while the console merges two backend sources. `geofence_alerts` (V9, `05-add-geofencing`'s own shipped table) is fully retired in this same migration: every existing row is copied into `alerts` (`alert_type` gains a "geofence_" prefix — `enter`→`geofence_enter` etc. — matching the console's already-built `AlertType` union, `apps/console/.../alerts/models/alert.model.ts`), then `geofence_alerts` is dropped. No second migration, no dual-write period, no two tables live for the same concept at once. `context` is a nullable `UUID REFERENCES geofences (id)` — a FOREIGN KEY on a nullable column in PostgreSQL only constrains its non-NULL values, so this preserves `geofence_alerts.geofence_id`'s exact referential-integrity guarantee for the three `geofence_*` types while staying NULL/unconstrained for the vehicle-level types this WU adds (speeding, excessive_idle) and for `offline` (reserved, not built until a later change). **Every `geofence_alerts` consumer was retargeted, not just the schema**: `JdbcGeofenceAlertWriter` (processor) now inserts into `alerts` (`GeofenceAlertType.storageValue()`, a new prefixed conversion, added alongside the existing unprefixed `wireValue()` MQTT publish shape — `MqttGeofenceAlertPublisher`'s own payload is deliberately untouched, only the persistence target changed); there was no `backend/api` geofence-alerts read endpoint to retarget — confirmed by reading the module directly, `AlertsService` (console) is still 100% mock data per the launch prompt, task 3.4/WU4's own job to wire against `alerts`. `acknowledged BOOLEAN NOT NULL DEFAULT false` is added now (ahead of WU4's own "marcado como atendida" endpoint) since design.md's "Panel de alertas" already names it as part of this same table's purpose — inert until WU4 builds the endpoint that sets it, avoiding a second migration touching this table for one column. Proven by `AlertSchemaTest` (CHECK constraint, FK behavior, null-context acceptance, `alert_silence_state`'s composite key) and a dedicated `AlertsGeofenceAlertsMigrationTest` (two-phase Flyway `target("11")` → seed a real `geofence_alerts` row → migrate the rest → assert it landed in `alerts` with the prefixed type and the old table is gone) — kept in its own file/container since `@Testcontainers`' static container is shared across every test method in a class, and this is the only test needing a two-phase migration.
- [x] 3.2 Alertas de exceso de velocidad y de ralentí excesivo — **WU3**: `AlertRuleDispatcher` (`backend/processor/.../alerts/`), wired into `JdbcTelemetryPositionWriter`'s SAME guarded live path `GeofenceRuleDispatcher`/`EtaRecalculationDispatcher` already use (a third consumer of the eligible-message subset — see task 2.4's resolution note and `JdbcTelemetryPositionWriter`'s own class comment). Speeding: `message.speedKmh() > FleetpulseAlertingProperties.speedLimitKmh()` (default 100.0), evaluated directly off the live telemetry reading — `vehicle_state` has no `speed_kmh` column of its own. Excessive idle: **reuses `vehicle_state`'s existing motion streaks (V7, `VehicleMotionStreakTracker`, live since `03-add-telemetry-ingest`) exactly as instructed, no second idle-detection mechanism invented** — `motion_state == IDLING && (now - low_speed_streak_started_at) >= excessiveIdleThreshold` (default 10m); `low_speed_streak_started_at` is the closest existing signal to "how long has this vehicle been continuously stationary" (IDLING requires being below the stop threshold, and that streak's start persists across the STOPPED→IDLING engine-on transition), documented here as the resolution since design.md never spells out the exact idle-duration source. **Design decision, documented per this project's "note deviations, don't silently freelance" convention**: `speedLimitKmh`/`excessiveIdleThreshold` are a single global `FleetpulseAlertingProperties` (`@ConfigurationProperties`), not a per-organization DB column — unlike `organizations.trip_stop_threshold_secs` (V10), which spec.md explicitly requires to vary per tenant, neither design.md nor spec.md asks a speed limit or idle threshold to vary per organization, so this follows `FleetpulseGeofencingProperties`/`FleetpulseMotionDetectionProperties`/`FleetpulseEtaProperties`/`FleetpulseTripsProperties`' own precedent instead.
- [x] 3.3 Ventana de silencio por (vehículo, tipo, contexto) para evitar repetición — **WU3**: `AlertSilenceEngine` (pure, `backend/processor/.../alerts/`), the same Spring-free/testable-without-a-database shape `GeofenceRuleEngine`/`FenceMembershipDetector` already established for damping logic. Implements design.md's own OR-worded rule literally — "no se emite otra igual hasta que pasa la ventana **o** la condición se resuelve y vuelve a darse" — as two independent ways to become eligible to fire again: (a) the condition was inactive last time and is active now (a fresh episode, fires immediately regardless of the window — spec.md's "Nueva alerta tras resolverse la condición" scenario), or (b) the condition has stayed continuously active and `FleetpulseAlertingProperties.silenceWindow` (default 15m) has elapsed since the last alert (a periodic re-notification for a still-ongoing episode — spec.md's "Exceso de velocidad sostenido" scenario, test 5.6).
