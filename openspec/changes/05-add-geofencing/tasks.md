## 2. Evaluación
- [x] 2.1 Consulta nativa única que devuelve todas las geocercas activas que contienen el punto — **WU2**: `GeofenceEvaluator.CONTAINING_GEOFENCE_IDS_SQL` (`backend/processor/.../geofencing/GeofenceEvaluator.java`). **Deviates from design.md's SQL sketch, documented per the "note deviations" convention**: design.md's sketch used `ST_Contains(area::geometry, ...)`, but `idx_geofences_area` (V8) is a GiST index built directly on the `geography`-typed `area` column — casting to `::geometry` per row makes that index unusable, and the planner silently falls back to a full sequential scan regardless of the index's existence. This was caught empirically: test 6.9 failed with `Seq Scan on geofences` on first run. Fixed by using `ST_Covers(area, point::geography)` instead, one of the two predicates the launch prompt explicitly allowed (`ST_Contains`/`ST_Covers`) — natively index-aware against a geography GiST index. Behavioral difference from `ST_Contains` is boundary inclusion only (a point exactly on the edge counts as covered), acceptable since WU3's oscillation damping absorbs boundary noise regardless of which side a single reading falls on.
- [x] 2.2 Comparación de conjuntos (dentro ahora vs. dentro antes) para derivar entradas y salidas — **WU2**: `GeofenceEvaluator.evaluate()` unions the containment query's result set with `vehicle_fence_state`'s previously-inside set (`is_inside = true` rows for the vehicle), then classifies each relevant geofence.
- [x] 2.3 Uso de `geo-core` para la decisión pura de transición por geocerca — **WU2**: reuses `FenceTransition.from(wasInside, isInside)`, already idle in `geo-core` since change `01-add-geo-core`. Zero new `geo-core` code needed, confirmed by the forecast.
- [x] 2.4 Evaluar solo si el mensaje es más reciente que el último evaluado para ese vehículo — **WU4**: `JdbcTelemetryPositionWriter.selectGeofenceEligibleMessages()` (`backend/processor/.../telemetry/JdbcTelemetryPositionWriter.java`). **Deviates from the forecast's literal architecture-decision wording, documented per the "note deviations" convention**: rather than reading `UPSERT_VEHICLE_STATE_SQL`'s own `batchUpdate()` return `int[]` (the SQL WHERE guard's own per-statement outcome), eligibility is computed in Java by mirroring `VehicleMotionStreakTracker.isNewer()`'s exact comparison against the SAME `knownMotionStates` snapshot already loaded for motion detection (zero extra queries) — the JDBC driver is free to report `Statement.SUCCESS_NO_INFO` instead of an exact 0/1 count for a batched statement depending on driver/batching mode, which would silently misclassify an accepted write as stale; mirroring the already-proven Java comparison sidesteps that risk while staying "the same pattern task 4.2 already established." Result feeds `GeofenceRuleDispatcher.evaluateAndDispatch()`.

## 3. Amortiguación de oscilación
- [x] 3.1 Confirmación temporal: marcar `pending_since` y confirmar tras N lecturas o T segundos — **WU3**: `FenceMembershipDetector.next()` (`backend/geo-core/src/main/java/dev/fleetpulse/geocore/`), a pure static function following `MotionDetector`'s exact shape (explicit prev-state + sample + config in, next-state out, no hidden mutation). `FenceMembershipConfig` carries `confirmationReadings` (int, ≥1) and `confirmationDuration` (`Duration`, non-negative) — validated in its compact constructor, mirroring `MotionConfig`. On the first differing reading, `pendingSince` is set to that reading's timestamp and `pendingReadingCount` to 1; each further consecutive differing reading increments the streak and re-checks both criteria (`streak >= confirmationReadings OR elapsed(pendingSince, observedAt) >= confirmationDuration`) — either one alone confirms. **Design gap found and resolved, documented per the established "note deviations, don't silently freelance" convention (same as WU2's `ST_Contains`→`ST_Covers` note)**: design.md's schema sketch for `vehicle_fence_state` only has a `pending_since` column, with no column to persist a reading-count streak, so "N lecturas consecutivas" cannot be reconstructed from the DB row alone across process restarts. WU3's pure `FenceMembershipState` record defines `pendingReadingCount` as part of its own state shape (not constrained by the current physical schema, since geo-core has zero DB awareness by design). **WU4 (wiring) must add a follow-up column (e.g. `pending_reading_count integer NOT NULL DEFAULT 0`) to `vehicle_fence_state` to persist this field**, or explicitly decide to rely on duration-only confirmation if it chooses not to extend the schema — either is a legitimate WU4-scope decision, not WU3's to make.
- [x] 3.2 Descartar la pendiente si la pertenencia vuelve al estado anterior antes de confirmar — **WU3**: same `FenceMembershipDetector.next()`. When a reading's effective membership matches the currently-confirmed state while a pending transition is in progress, the pending is discarded in full (`pendingSince`/`pendingReadingCount` reset to null/0) and `since` is left untouched at its original value — nothing is emitted, `FenceTransition.from(prev.inside(), next.inside())` evaluates to `NONE` for that step, matching the spec's "se descarta sin emitir nada." Proven directly (`discardsThePendingEntryWithoutEmittingAnythingWhenTheReadingRevertsToTheOriginalOutsideState`, `discardsThePendingExitWithoutEmittingAnythingWhenTheVehicleReturnsWithinTheBufferedBoundary`) and via a realistic multi-reading oscillation trace (`aVehicleStoppedOnTheBoundaryWithRealisticGpsDriftNeverConfirmsATransition`) mirroring `MotionDetectorTest`'s jitter-track test style.
- [x] 3.3 Margen espacial asimétrico: salida evaluada contra el polígono con buffer — **WU3**: `FenceMembershipSample(insideStrictBoundary, insideBufferedBoundary, observedAt)` carries both already-computed containment booleans for one reading (invariant enforced in its compact constructor: `insideStrictBoundary` can never be true while `insideBufferedBoundary` is false, since the buffered polygon always contains the strict one). `FenceMembershipDetector.next()` picks which one is authoritative purely from the current confirmed state: `prev.inside() ? sample.insideBufferedBoundary() : sample.insideStrictBoundary()` — entry is evaluated against the real (strict) polygon, exit only against the larger buffered polygon, exactly matching design.md's "se entra usando el polígono real, pero se sale solo al superar un polígono ligeramente mayor." A point between the two boundaries while confirmed inside never even starts a pending exit (`aPointWithinTheBufferButOutsideTheStrictBoundaryNeverStartsAPendingExit`) — this is the core anti-oscillation guarantee. **Scope boundary, consistent with WU3 being pure geo-core with zero DB/PostGIS awareness**: the actual `ST_Buffer(area, N)` query and buffer-distance configuration are WU4's concern (extending `GeofenceEvaluator`, WU2) to produce the two booleans this pure function consumes — geo-core owns only the hysteresis *decision* of which boundary result to trust, not the geometry computation itself.

## 4. Reglas y alertas
- [x] 4.1 Reglas `on_enter`, `on_exit`, `on_dwell` (permanencia superior a `dwell_secs`) — **WU4**: `GeofenceRuleEngine.next()` (`backend/processor/.../geofencing/GeofenceRuleEngine.java`), pure and Spring-free like `VehicleMotionStreakTracker`. Fires `ENTER`/`EXIT` the instant `FenceMembershipDetector` (WU3) confirms a transition matching the geofence's rule; fires `DWELL` once `Duration.between(next.since(), sample.observedAt())` reaches `dwell_secs`, tracked via a new `dwell_alerted` flag (gap resolution below) reset to `false` on every confirmed transition so a fresh stay can dwell-alert again. Dwell elapsed-time check is a plain `Duration.between` comparison, not a new geo-core class, per the launch prompt's own guidance mirroring `VehicleMotionStreakTracker`'s pattern of computing durations from timestamps rather than storing elapsed time. Unit-tested database-free in `GeofenceRuleEngineTest` (9 tests, all branches: enter/exit/no-match-rule/still-pending/dwell-before-threshold/dwell-at-threshold/no-double-dwell/dwell-reset-on-exit/fresh-stay-redwells).
- [x] 4.2 Publicación de alertas en `fleet/{orgId}/alerts` con QoS 2 — **WU4**: `AlertMqttConfig` + `MqttGeofenceAlertPublisher` (`backend/processor/.../geofencing/`). **No new ACL registration was needed, confirmed by reading 02-add-fleet-auth's dynsec bootstrap and credential services (not assumed)**: `docker/mosquitto/bootstrap-and-run.sh` already grants the processor's "internal-services" identity a wildcard `publishClientSend '#'` ACL, and `BrowserMqttCredentialService` already grants every dispatcher session a `subscribePattern fleet/{orgId}/#` ACL — both wildcards already cover `fleet/{orgId}/alerts` with zero ACL code changes; `DeviceCredentialService`'s narrower per-vehicle ACLs are correctly left untouched since devices have no business with alerts. Publish path: a long-lived Spring Integration `MqttPahoMessageHandler` outbound adapter (the outbound counterpart to `TelemetryMqttConfig`/`PresenceMqttConfig`'s inbound adapters — no outbound adapter existed anywhere in `processor` before this change), synchronous (`setAsync(false)`) so a failed publish is observable, topic set per-message via the `mqtt_topic` header (org id varies per alert). A broker-publish failure is caught and logged, never propagated into telemetry ingestion (alert persistence, task 4.3, happens first and is the durable record).
- [x] 4.3 Persistencia de alertas para el histórico y el panel de la consola — **WU4**: new `geofence_alerts` table (`V9__add_geofence_alerts_and_dwell_tracking.sql`) + `JdbcGeofenceAlertWriter` (plain `JdbcTemplate` insert, no JPA entity, same convention as `positions`). Indexed `(organization_id, occurred_at DESC)` and `(vehicle_id, occurred_at DESC)` for the console panel's newest-first read pattern.

**Two WU3-flagged gaps resolved in WU4, both documented in the launch prompt and resolved here:**
1. **`vehicle_fence_state` reading-count column** — resolved by adding the column (`pending_reading_count INTEGER NOT NULL DEFAULT 0`, `V9`), not by going duration-only: WU3's damping already implements the N-consecutive-readings confirmation criterion in geo-core, and leaving it unpersisted would silently make that code path dead in production (always losing to duration-only confirmation after every restart). A second new column, `dwell_alerted BOOLEAN NOT NULL DEFAULT false`, was also added (not flagged by WU3, a new WU4 finding) to track whether the `on_dwell` rule already fired for the current confirmed-inside stay — needed so a parked vehicle gets exactly one dwell alert, not one per message past the threshold.
2. **Buffered-boundary containment query** — resolved by extending `GeofenceEvaluator` (WU2), not duplicating it: `bufferedContainmentAmong(Set<UUID>, lat, lon, bufferMeters)` is a new, separately-scoped query bounded by `id = ANY(?)` (the handful of geofences a vehicle is already tracked against), deliberately NOT folded into the org-wide `CONTAINING_GEOFENCE_IDS_SQL` GiST-indexed query: `ST_Buffer(area, N)` is a per-row computed geography the GiST index on `area` cannot answer (the same reason task 2.1's own fix applies), so it stays a second query rather than risking the index-usability regression test 6.9 already caught once. Also added: `loadActiveMembershipStates()` (broader than `evaluate()`'s own "is_inside = true" set — also picks up an in-progress pending transition, needed so a reverting reading can discard it per task 3.2) and `loadRules()` (rule/dwell_secs metadata). `evaluate()` itself (tasks 2.1-2.3) is left unused by production wiring on purpose: publishing on its undamped transitions is exactly the oscillation failure WU3/WU4 exist to prevent; it remains as the direct, still-tested proof of the single-query/set-comparison/`FenceTransition` contract in isolation.

**Wiring (task 2.4's consequence)**: `GeofenceRuleDispatcher` (new, `@Component`) is called from `JdbcTelemetryPositionWriter.writeBatch()` with only the geofence-eligible subset of the flush batch. Per eligible message: `GeofenceEvaluator` supplies the strict/buffered containment + previous state + rule reads, `GeofenceRuleEngine` decides the next `FenceMembershipState` and which alerts fire, `JdbcVehicleFenceStateWriter` persists the state, and fired alerts are persisted (4.3) then published (4.2). One synchronous read-then-write round trip per (message, geofence) pair, not a batched compute-then-flush: a flush batch with two messages for the same vehicle needs its second message's evaluation to see the first message's already-persisted `vehicle_fence_state` row, and a vehicle can be tracked against multiple geofences at once — a synchronous write on the same `JdbcTemplate`/connection gives correct chaining for free through ordinary read-after-write. `organizationId` (needed for the alert topic and the containment query) is resolved from `vehicles.organization_id`, never from the MQTT topic's org segment — `TelemetryMessage` has never carried an org id (change 03's own contract), and the topic segment is an unvalidated caller-supplied label, not a trustworthy source of the real organization.
