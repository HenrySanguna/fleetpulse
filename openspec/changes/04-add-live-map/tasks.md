## 2. Arranque snapshot + stream
- [x] 2.1 `GET /api/fleet/state` en `api`: estado actual de todos los vehículos de la organización — **WU2, extended per the documented gap**: `FleetStateController`/`FleetStateService` (`backend/api/src/main/java/dev/fleetpulse/api/fleet/`) return every vehicle in the requesting dispatcher's organization (`VehicleRepository.findByOrganizationId`, new) joined with its latest `vehicle_state` row via `VehicleStateJdbcReader` (raw JDBC — `vehicle_state` has no JPA entity, same reason `processor`'s `JdbcTelemetryPositionWriter`/`JdbcVehiclePresenceWriter` bypass JPA for this PostGIS-geography-backed table); a vehicle with no `vehicle_state` row yet still appears (offline, null fields), never hidden. Extension: `GET /api/vehicles/{id}/track` (`VehicleTrackController`/`VehicleTrackService`) runs `Geo.simplifyTrack` (geo-core, already existed idle since change 03) against `positions` (via `PositionJdbcReader`, same raw-JDBC reasoning) with a configurable tolerance (`FleetpulseTrackProperties`, default 15m); vehicle ownership is checked the same 404-not-403 way `DeviceCredentialController#deviceInOwnOrgOrThrow` (02-add-fleet-auth) already does, so a vehicle in another organization does not leak its existence. `vehicle_state` has no `speed_kmh`/`heading` columns (only `positions`, the history table, does) — the snapshot DTO honestly reflects that; the live map gets those fields from the MQTT telemetry stream directly (WU1/WU3), matching proposal.md's core decision that the backend is not in the live data path. `libs/api-client` regenerated (`npm run generate:api-client`, verified in sync with `--check`).
- [x] 2.2 Secuencia de arranque: suscribir → bufferizar → snapshot → aplicar buffer → directo — **WU3**: `FleetStartupService` (`apps/console/src/app/features/live-map/services/fleet-startup.service.ts`). **Resolved design gap**: `MqttConnectionService.connect(organizationId)` (WU1) needs an `organizationId`, but `GET /api/mqtt/credentials`'s response never echoes it and design.md's own sequence starts at "obtain MQTT credentials" without addressing this. Resolved by resolving the current dispatcher first via the already-generated `DispatcherSessionControllerService.me()` (`GET /api/dispatchers/me`, from change 02) and reading `organizationId` off `DispatcherSelfView`, before calling `connect()`. Mechanics: `toObservable(mqttConnectionService.status).pipe(filter(status === 'connected'), switchMap(() => runStartupCycle()))` — `status()` reaching `'connected'` is the signal that WU1's client already subscribed (it does so synchronously in its own `'connect'` handler, task 1.4), so a fresh RxJS `Subject`-backed `messages$` subscription starts collecting into an in-memory buffer array (not yet applied) at that point, immediately followed by `GET /api/fleet/state`; on that response, `FleetStore.applySnapshot()` runs, then every buffered message is replayed through `FleetStore.applyUpdate()` (task 2.3's guard lives there), then the same subscription keeps forwarding every subsequent live message directly to `applyUpdate()` — no unsubscribe/resubscribe race between "buffering" and "live" because it is the same subscription the whole time, just a boolean flag switching what it does with each message. A snapshot-fetch failure is logged, not thrown, specifically so it cannot propagate through `switchMap` and permanently kill future reconnect cycles (see `fleet-startup.service.ts`'s own comment); the known tradeoff is that this cycle does not itself retry a failed snapshot fetch, recovery relies on the next actual MQTT reconnect.
- [x] 2.3 Guarda de monotonía al aplicar el buffer (descartar lo anterior al snapshot) — **WU3**: lives in `FleetStore.applyUpdate()` (not in the startup service), so it applies uniformly to both the buffer-replay path and the live-stream path through the exact same code — there is exactly one place that decides "is this stale". Compares `Date.parse()` of the two ISO-8601 instants (not the raw strings) per-vehicle, since two valid ISO-8601 UTC instants don't always sort correctly as plain strings (e.g. differing fractional-second precision at the same whole second). Only telemetry updates are guarded: presence/status messages (`fleet/.../status`) carry no `recordedAt` in their wire payload at all — `PresencePayload(Boolean online)`, change 03 — MQTT's own retained-message semantics already make the latest publish win, matching design.md's reconnection note.
- [x] 2.4 Repetir el ciclo completo al reconectar — **WU3**: falls out of 2.2's mechanics for free — `MqttConnectionService.status()` transitions to `'connected'` again on reconnect exactly the same way it does on first connect (WU1), so the single `filter(status === 'connected')` stream above covers both cases without special-casing "is this a reconnect". `switchMap` tears down the previous cycle's subscriptions (including its "apply live directly" forwarding) the instant a new `'connected'` status arrives, which is exactly the "stop trusting the old state, start buffering fresh" behavior this task asks for.
