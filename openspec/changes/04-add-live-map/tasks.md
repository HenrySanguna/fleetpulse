**Gap discovered, not in the original task list, and the single most significant finding of this WU**: `libs/api-client`'s generated `*ControllerService` methods (`DispatcherSessionControllerService.me()`, `MqttCredentialsControllerService.credentials()`, `FleetStateControllerService.state()`, and by the same mechanism every other generated method that doesn't restrict its OpenAPI response to one specific content type) silently request `responseType: 'blob'` instead of `'json'`. Root cause: `Configuration.selectHeaderAccept(['*/*'])` (`libs/api-client/src/configuration.ts`) falls back to the literal `'*/*'` when no candidate content type matches its own `isJsonMime()` regex, and `'*/*'` itself fails that same regex, so the generated method's own `responseType_` computation lands on the `'blob'` branch. The real backend still replies with genuine JSON regardless (Spring's default Jackson converter does not care what Accept header the client sent), so this was NEVER visible as an HTTP error: every caller silently received a `Blob` object typed as its expected DTO, with every property read off it — `dispatcher.organizationId`, `credentials.username`/`wsUrl`, `snapshot.vehicles` — silently `undefined`. This broke `FleetStartupService.start()` (task 2.2) completely, silently, in the REAL running app (not a test artifact): `if (dispatcher.organizationId) { this.mqttConnectionService.connect(...) }` was always false, so `MqttConnectionService.connect()` was NEVER actually called since WU3 first shipped it — the browser MQTT client has never once connected in a real browser session before this WU, confirmed by writing this WU's own diagnostic instrumentation (a temporary `page.on('console'/'websocket')`-based probe script, written, used, and deleted, matching WU9's own throwaway-harness precedent) that showed zero `/api/mqtt/credentials` requests ever firing. None of WU1–WU5's own unit tests could have caught this: every one of them mocks the generated `*ControllerService` directly at Angular's DI boundary (`{ provide: DispatcherSessionControllerService, useValue: { me: () => of({...}) } }`-style), never exercising the real `HttpClient` request/response-type negotiation underneath — exactly the same class of gap WU5's own apply-progress already flagged once for the `mqtt` package's browser-vs-CJS export shape. **Two fix approaches were tried and rejected before the one that shipped**: (1) an `HttpInterceptorFn` rewriting the outgoing request's `responseType` to `'json'` throws `NG02807: Response is not a Blob` at runtime under `provideHttpClient(withFetch())`, because `HttpClient.request()`'s own body-extraction `switch (req.responseType)` (confirmed by reading `@angular/common`'s compiled `_module-chunk.mjs` directly) runs against the ORIGINAL, caller-constructed request object AFTER the entire interceptor chain completes — an interceptor cannot change what that outer switch believes the caller asked for, no matter whether it rewrites the request or the response body; - [x] 2.2 Secuencia de arranque: suscribir → bufferizar → snapshot → aplicar buffer → directo — **WU3**: `FleetStartupService` (`apps/console/src/app/features/live-map/services/fleet-startup.service.ts`). **Resolved design gap**: `MqttConnectionService.connect(organizationId)` (WU1) needs an `organizationId`, but `GET /api/mqtt/credentials`'s response never echoes it and design.md's own sequence starts at "obtain MQTT credentials" without addressing this. Resolved by resolving the current dispatcher first via the already-generated `DispatcherSessionControllerService.me()` (`GET /api/dispatchers/me`, from change 02) and reading `organizationId` off `DispatcherSelfView`, before calling `connect()`. Mechanics: `toObservable(mqttConnectionService.status).pipe(filter(status === 'connected'), switchMap(() => runStartupCycle()))` — `status()` reaching `'connected'` is the signal that WU1's client already subscribed (it does so synchronously in its own `'connect'` handler, task 1.4), so a fresh RxJS `Subject`-backed `messages$` subscription starts collecting into an in-memory buffer array (not yet applied) at that point, immediately followed by `GET /api/fleet/state`; on that response, `FleetStore.applySnapshot()` runs, then every buffered message is replayed through `FleetStore.applyUpdate()` (task 2.3's guard lives there), then the same subscription keeps forwarding every subsequent live message directly to `applyUpdate()` — no unsubscribe/resubscribe race between "buffering" and "live" because it is the same subscription the whole time, just a boolean flag switching what it does with each message. A snapshot-fetch failure is logged, not thrown, specifically so it cannot propagate through `switchMap` and permanently kill future reconnect cycles (see `fleet-startup.service.ts`'s own comment); the known tradeoff is that this cycle does not itself retry a failed snapshot fetch, recovery relies on the next actual MQTT reconnect.
- [x] 2.3 Guarda de monotonía al aplicar el buffer (descartar lo anterior al snapshot) — **WU3**: lives in `FleetStore.applyUpdate()` (not in the startup service), so it applies uniformly to both the buffer-replay path and the live-stream path through the exact same code — there is exactly one place that decides "is this stale". Compares `Date.parse()` of the two ISO-8601 instants (not the raw strings) per-vehicle, since two valid ISO-8601 UTC instants don't always sort correctly as plain strings (e.g. differing fractional-second precision at the same whole second). Only telemetry updates are guarded: presence/status messages (`fleet/.../status`) carry no `recordedAt` in their wire payload at all — `PresencePayload(Boolean online)`, change 03 — MQTT's own retained-message semantics already make the latest publish win, matching design.md's reconnection note.
- [x] 2.4 Repetir el ciclo completo al reconectar — **WU3**: falls out of 2.2's mechanics for free — `MqttConnectionService.status()` transitions to `'connected'` again on reconnect exactly the same way it does on first connect (WU1), so the single `filter(status === 'connected')` stream above covers both cases without special-casing "is this a reconnect". `switchMap` tears down the previous cycle's subscriptions (including its "apply live directly" forwarding) the instant a new `'connected'` status arrives, which is exactly the "stop trusting the old state, start buffering fresh" behavior this task asks for.
